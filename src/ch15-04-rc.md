## `Rc<T>`, o Ponteiro Inteligente de Contagem de Referências

Na maioria dos casos, a propriedade é clara: você sabe exatamente qual variável
possui um determinado valor. No entanto, há casos em que um único valor pode ter
vários proprietários. Por exemplo, em estruturas de dados de grafos, várias arestas
podem apontar para o mesmo nó, e esse nó é conceitualmente propriedade de todas as
arestas que apontam para ele. Um nó não deve ser limpo a menos que não tenha nenhuma
aresta apontando para ele e, portanto, nenhum proprietário.

Você precisa habilitar a propriedade múltipla explicitamente usando o tipo do Rust
`Rc<T>`, que é uma abreviação para _reference counting_ (contagem de referências). O tipo
`Rc<T>` monitora o número de referências a um valor para determinar se o valor
ainda está em uso ou não. Se houver zero referências a um valor, o valor poderá ser
limpo sem que nenhuma referência se torne inválida.

Imagine o `Rc<T>` como uma televisão em uma sala de estar. Quando uma pessoa entra para
assistir TV, ela a liga. Outros podem entrar na sala e assistir à TV. Quando a última
pessoa sai da sala, ela desliga a TV porque ela não está mais sendo usada.
Se alguém desligar a TV enquanto outras ainda estiverem assistindo, haverá
um alvoroço por parte dos telespectadores restantes!

Usamos o tipo `Rc<T>` quando queremos alocar alguns dados no heap para
várias partes do nosso programa lerem e não conseguimos determinar em tempo de compilação
qual parte terminará de usar os dados por último. Se soubéssemos qual parte terminaria
por último, poderíamos simplesmente tornar essa parte a proprietária dos dados, e as
regras normais de propriedade impostas em tempo de compilação entrariam em vigor.

Note que o `Rc<T>` deve ser usado apenas em cenários de thread única (single-threaded). Quando discutirmos
concorrência no Capítulo 16, veremos como fazer a contagem de referências em
programas multithread.

As variantes `Cons` possuem os dados que contêm, então, quando criamos a lista `b`, `a`
é movida (`moved`) para `b` e `b` passa a ser dono de `a`. Então, quando tentamos usar `a` novamente ao
criar `c`, não temos permissão porque `a` foi movido.

Podemos alterar a definição de `Cons` para conter referências, mas nesse caso
teríamos que especificar parâmetros de tempo de vida (*lifetimes*). Ao especificar parâmetros de tempo de vida,
estaríamos especificando que cada elemento da lista viverá pelo menos tanto
quanto a lista inteira. Este é o caso para os elementos e listas na Listagem 15-17, mas não em todos os cenários.

Em vez disso, mudaremos nossa definição de `List` para usar `Rc<T>` no lugar de
`Box<T>`, como mostrado na Listagem 15-18. Cada variante `Cons` agora conterá um valor
e um `Rc<T>` apontando para uma `List`. Quando criarmos `b`, em vez de assumir a
propriedade de `a`, clonaremos o `Rc<List>` que `a` está segurando,
aumentando assim o número de referências de um para dois e permitindo que `a` e `b`
compartilhem a propriedade dos dados naquele `Rc<List>`. Também clonaremos `a` ao
criar `c`, aumentando o número de referências de dois para três. Cada vez
que chamamos `Rc::clone`, a contagem de referência para os dados dentro do `Rc<List>`
aumenta, e os dados não serão limpos a menos que haja zero referências a eles.

Precisamos adicionar uma instrução `use` para trazer `Rc<T>` para o escopo, porque ele não
está no *prelude*. No `main`, criamos a lista contendo `5` e `10` e a armazenamos
em um novo `Rc<List>` em `a`. Então, quando criamos `b` e `c`, chamamos a
função `Rc::clone` e passamos uma referência para o `Rc<List>` em `a` como argumento.

Poderíamos ter chamado `a.clone()` em vez de `Rc::clone(&a)`, mas a convenção do Rust
é usar `Rc::clone` neste caso. A implementação de
`Rc::clone` não faz uma cópia profunda (*deep copy*) de todos os dados como a maioria das implementações
de `clone` dos tipos faz. A chamada para `Rc::clone` apenas incrementa a
contagem de referências, o que não leva muito tempo. Cópias profundas de dados podem levar
muito tempo. Usando `Rc::clone` para a contagem de referências, podemos distinguir visualmente
entre os tipos de clones de cópia profunda e os tipos de clones que aumentam
a contagem de referências. Ao procurar problemas de desempenho no código, só precisamos considerar os clones de cópia profunda e podemos desconsiderar as chamadas para
`Rc::clone`.

Podemos ver que o `Rc<List>` em `a` tem uma contagem de referências inicial de 1;
então, cada vez que chamamos `clone`, a contagem sobe em 1. Quando `c` sai do
escopo, a contagem desce em 1. Não precisamos chamar uma função para diminuir
a contagem de referências como precisamos chamar `Rc::clone` para aumentá-la:
a implementação da *trait* `Drop` diminui a contagem de referências
automaticamente quando um valor `Rc<T>` sai do escopo.

O que não podemos ver neste exemplo é que quando `b` e depois `a` saem do escopo
no final do `main`, a contagem é 0, e o `Rc<List>` é limpo
completamente. O uso de `Rc<T>` permite que um único valor tenha vários proprietários, e
a contagem garante que o valor permaneça válido enquanto qualquer um dos proprietários
ainda existir.

Por meio de referências imutáveis, o `Rc<T>` permite que você compartilhe dados entre várias
partes do seu programa apenas para leitura. Se o `Rc<T>` permitisse que você tivesse várias
referências mutáveis também, você poderia violar uma das regras de empréstimo discutidas
no Capítulo 4: Múltiplos empréstimos mutáveis para o mesmo lugar podem causar *data races* (corridas de dados) e inconsistências. Mas ser capaz de mutar dados é muito útil! Na próxima
seção, discutiremos o padrão de mutabilidade interior (*interior mutability*) e o tipo `RefCell<T>`
que você pode usar em conjunto com um `Rc<T>` para contornar essa restrição de imutabilidade.
